# Political Philosophy Presentations

This folder is structured as a static GitHub Pages site.

## Publish it

1. Create a GitHub repository, such as `political-philosophy`.
2. Upload the site files and folders while preserving their structure.
3. In the repository, open **Settings → Pages**.
4. Under **Build and deployment**, choose **Deploy from a branch**.
5. Select the `main` branch and the `/ (root)` folder.

The live address will be:

```text
https://YOUR-USERNAME.github.io/political-philosophy/
```

The root `index.html` is the subject landing page. Choose **Political Philosophy** to open the existing course library; the library's presentation files remain in `Presentations/`, and the shared `presentation-polish.css` and `presentation-polish.js` files must stay beside those presentation HTML files. The Ethics page is ready for additional presentations.

## Editing

Edit a presentation HTML file locally or through GitHub, then commit the change. GitHub Pages will redeploy the updated version automatically.

Only upload files you want to make public. GitHub Pages sites are publicly accessible.

## Presentation authoring standards

Apply these rules to every new or revised deck in `Presentations/`:

- For every newly created presentation, add a linked card/button to the appropriate module or topic section in the root `index.html`. Use the presentation's exact path, URL-encode spaces when needed, include a clear title and useful `data-search` keywords, and verify that the button opens the correct deck.
- Do not create standalone quotation or epigraph slides. Put a short quotation on an explanatory slide or in the speaker notes, with the surrounding claim doing the teaching.
- Do not create standalone rhetorical-question or quasi-title transition slides. Move the transition into a concise section title or an explanatory content slide, then proceed directly to the argument.
- Design for classroom projection, distance reading, and instructional pacing. Use `Presentations/Justifying the State - Introduction and Social Contract.html` as a baseline for large, readable type, but not as a density target. Use the available screen to make the one idea currently being taught unmistakable. Spaciousness is appropriate when it helps students identify and process that idea. Scale headings, body copy, rows, and explanatory elements until they are comfortably legible without clipping or overflow. Do not copy the reference deck’s theme, colors, typography, or layout unless explicitly requested.
- Give every slide and every staged reveal one teaching move: a definition, claim, example, objection, comparison, or implication. Split a list or argument when students would need to read ahead in order to follow the lecture. A lower slide count never justifies presenting several independent ideas simultaneously.
- When a deck distinguishes types of something, make the organizing concept prominent. For example, `Tacit Consent` must appear in the title or another large, high-contrast element. A small eyebrow, caption, or decorative label may reinforce the category, but it cannot be the only place where the central concept appears.
- Build a short explanatory arc for every major contested concept: what it is, what it is meant to establish, its strongest rationale or example, the objection, and the consequence. Omit only stages that would repeat rather than clarify. Keep section-title slides minimal, but do not use that rule to compress the explanatory arc into a single dense content slide.
- Preserve the source material's meaning, distinctions, and established terminology. Do not rename key concepts or simplify them in ways that change the argument. At the same time, do not turn the deck into a 1:1 transcription of the chapter: assume students have already read it, and use the presentation to simplify, clarify, and organize the ideas through concise claims, examples, comparisons, and visual emphasis. A successful lecture deck should be easier to follow in real time and meaningfully different in form and pacing from the source while remaining faithful to it.
- Use progressive disclosure when successive elements belong to the same teaching move. The first view should show the concept and the first point only; each next action reveals one additional point while preserving what the class has already discussed. Reserve every later element's final position before the first reveal. A reveal must not move, resize, rewrap, or realign anything already visible; new material should fill a preplanned empty area. Use a new slide, rather than another reveal, for a new claim or explanatory task. Do not use animation merely as decoration.
- Treat supplied materials as research, not as a topic of the presentation. State their ideas and arguments directly. Do not write “the reading,” “the chapter,” “the source,” or “the author” in visible slide copy or presenter-facing instructional notes. Name a thinker or work only when the attribution itself matters. Keep source citations in speaker notes or a references slide rather than using source language to narrate the lesson.
- Test every reveal stage in full-screen presentation mode. At each stage, a student should be able to identify the current concept within two seconds; unrevealed material must not compete for attention; visible text must remain readable and unclipped; and every already-visible element must stay fixed in place.
- Choose a visual theme that is materially different from the themes already used in the library. Inspect the existing decks before designing a new one; do not default to the green/light-green palette or reuse the same typography, background treatment, and decorative motif unless the user explicitly requests a template match.
- Keep section-title slides minimal. Let the following explanatory content begin the argument; it may develop across several paced slides or reveal stages.
